# 조사 B — 문서·텍스트·UI 합성 데이터 생성기의 "실데이터로 전이되는 다양성" 확보 방식

작성일 2026-09-11. 대상: 우리 HTML 서식 생성기(카드 93종 × 문서유형 26종, 이산 테마축 3–6값, 폰트 3종, 라벨어 ~90, 선택지 36) → FFDNet-L(imgsz 1600) 학습. 합성 홀드아웃 recall 99.9 vs 실서식 90.4의 격차를 줄이기 위한 문헌 근거.

공통 진단: 아래 논문들은 예외 없이 **(a) 요소 단위 랜덤화의 축 수**, **(b) 각 축의 값 개수(연속 vs 3–6개 이산)**, **(c) 실코퍼스에서 끌어온 어휘·요소 풀**의 세 가지로 전이를 얻었다. 우리 생성기는 세 항목 모두 하한에 있다(폰트 3, 이산축, 라벨어 90).

## 1. 문서 레이아웃 합성

### DocLayout-YOLO / DocSynth-300K — arXiv:2410.12628
M6Doc 테스트셋 약 2,800페이지를 74개 요소 카테고리로 쪼개 "요소 풀"을 만든 뒤, 페이지 합성을 2D bin-packing으로 푼다(Mesh-candidate BestFit). 매 페이지마다 (1) 요소 크기별 층화 샘플링으로 후보 집합 추출, (2) 현재 레이아웃에서 빈 격자(mesh) 구성, (3) 채움률 최대인 mesh–candidate 쌍 선택, (4) 크기 조건을 만족하는 쌍이 없을 때까지 반복 후 중심 랜덤 스케일링. 랜덤화 대상은 요소 카테고리·개수(N≤15, 소형 요소 ≤5)·배치 위치·최종 스케일이며, 100개 미만 희소 카테고리는 flip·밝기·크롭·elastic으로 증강해 풀을 채운다. 핵심은 "순수 랜덤이 아니라 채움률·정렬(미학)을 제약으로 둔 랜덤"이다.
- 핵심 수치(YOLOv10-m 사전학습, DocStructBench mAP): 무사전학습 80.5/70.2/68.9/89.9 → Random-300k 80.5/71.2/68.1/89.6(거의 무효) → Diffusion(LACE)-300k 80.7/71.9/68.9/89.3(일부 도메인만) → **DocSynth-300K 82.1/71.5/69.3/90.3(4개 도메인 전부 상승)**. PubLayNet-300k(81.0)·DocBank-400k(81.6)보다도 높음. 저자 해석: 단일 분포 실데이터(학술지만)는 과적합, 요소 카테고리 74종 + 단/다단 혼합이 전이의 원천.
- **우리 적용:** 카드 배치를 문법 순서 고정이 아니라 "빈 영역에 채움률 기준으로 카드 끼워넣기" 모드를 일부 비율(예 30%)로 섞는다. 실서식 149p에서 크롭한 실제 부품(표·체크박스 군·서명란)을 요소 풀에 추가해 합성 페이지에 붙이는 "실요소 콜라주"가 DocSynth와 정확히 같은 구조. Random 베이스라인이 무효였다는 점은 "무작위만 늘리면 된다"는 가설을 기각하니 정렬 제약을 유지해야 한다.

### Synthetic Document Generator for Annotation-free Layout Recognition — arXiv:2111.06016 (Pattern Recognition 2022)
문서의 모든 물리 요소(단 수, 폰트, 크기, 간격, 색, 위치)를 베이지안 네트워크의 확률변수로 두고 "확률적 템플릿" 계층으로 샘플링한다. 합성만으로 학습한 레이아웃 검출기가 실문서 학습 모델과 동급 성능을 냈다고 보고(PubLayNet 기준).
- **우리 적용:** 우리 theme 축(3–6값)을 조건부 분포로 바꾸는 근거. 예: 폰트 크기 → 셀 높이 → 패딩이 종속 샘플링되도록 하면 "존재하지만 우리 격자에는 없는" 조합이 생성된다.

### DocGenome — arXiv:2406.11633 / M6Doc / PubLayNet·DocBank
DocGenome은 arXiv LaTeX 소스 50만 편을 자동 렌더·라벨(13 레이아웃 속성). PubLayNet·DocBank도 실PDF의 XML/LaTeX 정합으로 얻은 "실데이터형 대량 라벨"이며 합성 랜덤화는 없다. DocLayout-YOLO 표에서 이들이 DocSynth보다 낮은 이유가 바로 단일 도메인이다.
- **우리 적용:** 우리 44 손전사 HTML 복제본은 이 부류(실구조·자동라벨)에 해당. 그대로 학습에 섞는 것보다 DocSynth식 요소 풀의 원천으로 쓰는 게 효율적.

### LayoutTransformer(ICCV 2021) / LayoutDM(CVPR 2023) / LACE
학습 기반 레이아웃 샘플러. DocLayout-YOLO 표 4에서 LACE(diffusion)로 만든 300k는 특정 도메인만 개선하고 전체 전이는 DocSynth에 미달했다.
- **우리 적용:** 생성 모델 도입은 후순위. 규칙 기반 bin-packing + 실요소 풀이 더 싸고 효과가 검증됨.

## 2. 텍스트 렌더링 합성

### SynthText — arXiv:1604.06646 (CVPR 2016)
배경 8,000장에 Newsgroup20 텍스트(단어/≤3줄/≤7단락)를 80만 장 합성. gPb-UCM 세그먼트+CNN 깊이로 평면 영역을 찾고 표면 법선에 맞춰 투시 변환. 폰트는 Google Fonts에서 무작위(후속 논문들이 약 1,200종으로 인용), 색은 IIIT5K 팔레트, 20% 테두리, 그림자·커닝·크기 랜덤. 합성만으로 ICDAR2013 F 84.2.
- **우리 적용:** "색을 실데이터 팔레트에서 샘플링"이 우리에게 그대로 옮겨진다 — 실서식 149p 픽셀에서 선색·배경 회색·음영 팔레트를 추출해 CSS 색으로 쓴다.

### UnrealText — arXiv:2003.10608 (CVPR 2020)
3D 엔진 30개 장면에서 60만 장, 다국어(한국어 포함 10개) 버전 60만 장. 카메라 시점은 충돌 회피 3D 랜덤워크, 조명은 강도·색·방향·안개까지 랜덤, 폰트는 SynthText와 같은 Google Fonts 풀.
- 핵심 수치(검출 F1, 10K장 사전학습): SynthText 46.3/60.8/38.9 → VISD 64.3/74.8/51.4 → **UnrealText 65.2/78.3/54.2**(IC15/IC13/MLT17). 시점 랜덤화·환경 랜덤화 각각을 끄면 모든 데이터 규모에서 하락. 같은 폰트·같은 코퍼스인데 "장면·조명 다양성"만으로 18–20점 차이.
- **우리 적용:** 폰트·어휘를 고정하더라도 "촬영·스캔 조건" 축(기울기, 그림자, 밝기 기울기, 종이 질감, JPEG)이 독립적으로 큰 몫을 한다. 렌더 후처리 파이프라인을 SynthDoG 수준으로 넣을 근거.

### SynthDoG (Donut) — arXiv:2111.15664
Donut의 합성기. config_ko.yaml 실측값: 배경 이미지 + 가우시안 블러 σ∈[0,10], 종이 알파 [0,0.2], 문서 short_size [480,1024], 텍스트 스케일 [0.0334,0.1](연속), 행 ≤10·열 ≤3, 채움률 [0.5,1], 정렬 {left,right,center}, 색 확률 0.2(회색 [0,64] / RGB 전역), elastic α[0,1]·σ[0,0.5], 노이즈 [0,8], 원근 가중치, 모션블러 p=0.5 커널 {3,5} 각도 [0,360], 대비 [1,1.5], 밝기 [-48,0], 그림자 [0,160], JPEG 품질 [50,95]. 코퍼스는 kowiki.txt(위키 전체), 폰트는 `resources/font/ko` 디렉터리 전체.
- **우리 적용:** 우리 생성기의 축은 대부분 3–6값 이산인데 SynthDoG는 **모든 축이 연속 구간**이다. 가장 저렴한 변경: `hwp_theme.py`의 이산 테마값을 구간 균등/정규 샘플링으로 바꾸고, 렌더 후 SynthDoG의 후처리 블록(elastic·모션블러·밝기·그림자·JPEG)을 그대로 이식한다. 한국어 코퍼스 소스로 kowiki를 라벨어 외 "본문·안내문" 채움에 쓸 수 있다.

### SynthTIGER — arXiv:2107.09313 (ICDAR 2021)
5단계(글꼴 형태→스타일/텍스처→변형→전경·중간·배경 블렌딩→후처리). **폰트 3,568종**(MJSynth 1,400·SynthText 1,200 대비). 제거 실험(총 정확도 변화): 텍스처 블렌딩 −3.9, 후처리 −5.2(불규칙 텍스트 −11.9), 변형 −2.6, 여백 −1.9, 중간 텍스트 −0.7. 길이 분포 증강 +2.1, 문자 분포 증강(희소 문자) +2.5(일본어). 10M장으로 MJ+ST 15.9M(85.1)보다 높은 85.9.
- **우리 적용:** (1) 폰트 3종은 문헌 최소치의 1/400. 한글 무료 폰트(눌러쓴 고딕·명조·바탕·궁서·나눔·본고딕·프리텐다드 등) 100종+ 확보가 1순위. (2) "여백(margin) 제거 −1.9"는 우리 셀 패딩·행 높이 랜덤화의 직접 근거. (3) 길이·문자 분포 증강은 우리 라벨어의 길이 분포(2–4자 편중)를 실OCR 토큰 길이 분포에 맞추라는 뜻.

## 3. 웹/UI 생성기 — LLM이 쓰는 HTML

### WebSight — arXiv:2403.09029
Mistral-7B가 수백만 개의 "웹사이트 콘셉트"(업종·색·배치 변형)를 먼저 쓰고, Deepseek-Coder-33B가 콘셉트별 Tailwind HTML을 생성(v0.1 823K → v0.2 2M). 2단계 분리로 어휘·주제 다양성을 소형 모델이, 코드 품질을 대형 모델이 담당. v0.2는 색 사각형 대신 Unsplash 실사진.
- **우리 적용:** 우리 문법(카드·문서유형)을 "콘셉트 → HTML" 2단계로 확장: LLM에 실서식 OCR 토큰 4,000개와 문서유형을 주고 "카드 시퀀스+라벨어 집합"(콘셉트)을 대량 생성 → 기존 렌더러가 HTML화. 렌더러는 그대로, 상류 어휘·순서만 넓힌다.

### Design2Code — arXiv:2403.03163 (NAACL 2025) / WebCode2M — arXiv:2404.06369 / Web2Code — arXiv:2406.20098
Design2Code는 실웹 484p 벤치마크; CogAgent-18B를 WebSight 20%로 미세조정한 Design2Code-18B가 Block-Match 78.5로 Gemini Pro Vision(80.2)에 근접. C4 실웹 코드로 학습하면 "길고 노이즈가 많아 불안정, 합성보다 낮음". 반면 WebCode2M은 합성 WebSight(평균 647토큰·19태그·DOM 깊이 5) vs 실웹(31,216토큰·158태그·깊이 13)의 격차를 지적하고 실데이터 학습 WebCoder가 TreeBLEU 0.35 vs 0.04로 압도. Web2Code는 WebSight·Pix2Code를 LLM으로 정제·재생성해 1.18M.
- **우리 적용:** 두 결론이 상충하는 듯하지만 교훈은 하나 — **합성은 "깨끗하지만 단순"으로 수렴**한다. 우리 합성 페이지의 구조 복잡도(카드 수·중첩 표 깊이·병합 셀 비율)를 실서식 44 복제본 통계와 맞추는 히스토그램 매칭이 필요하다.

### OS-Atlas — arXiv:2410.23218 / Jedi(OSWorld-G) — arXiv:2505.13227
OS-Atlas: FineWeb 400만 페이지를 1920×1080으로 렌더, HTML에서 클릭 요소 좌표 추출, 5개 플랫폼 230만 스크린샷·1,300만 요소. 페이지당 요소 ≤10으로 상한을 둬 다양성 유도; 웹만으로 사전학습하면 타 플랫폼으로 일반화 실패. Jedi: Material UI 예제 코드를 LLM이 과업별 변형→React 렌더로 정밀 GT(31K 이미지·385K 대화), 아이콘은 OS 바이너리에서 추출, 레이아웃은 Figma 내보내기. 데이터 비율 10→100%에서 포화 없음, **아이콘+컴포넌트+레이아웃 혼합이 단일 유형 확장보다 안정적 향상**. SeeClick/OS-Atlas 합성분은 UI-TARS-72B로 품질 필터.
- **우리 적용:** (1) "컴포넌트 코드를 LLM이 변형→렌더→GT 자동" 은 우리 `components.py` 부품 함수에 그대로 적용 가능(LLM에게 부품 CSS 변형본 N개 작성 지시, lint 통과분만 채택). (2) 페이지당 필드 수 상한·하한을 실서식 분포에서 뽑아 강제.

### Hallucination-Free GUI Grounding — arXiv:2608.09654
프리즌 MLLM이 지시를 레이아웃 단서 기술로 확장하고, 회귀 없는 매칭 모델이 후보와 대조하는 방법론 논문. 데이터 다양성에 관한 내용은 초록·본문 요약에서 확인되지 않아 본 주제에는 기여 없음.

## 4. 서식(Form) 특화

### CommonForms / FFDNet — arXiv:2509.16506
Common Crawl PDF 790만 → AcroForm/XFA 76.2만 → 버튼 외 필드 보유 5.9만 문서·48만 페이지. 다양성은 랜덤화가 아니라 **웹 규모 실데이터 자체**에서 온다: 비영어 1/3(광둥어 12.6, 독어 6.8, **한국어 2.6%**), 14 도메인 중 최대 25% 이하. 해상도 절제(10k 페이지): 640→1536px에서 전체 AP 42.7→62.1(+20), 서명 26.7→65.3. 필터링된 10k가 비필터 데이터보다 +4 mAP. FFDNet-L(YOLO11, 25M, 1216px, 300ep) 전체 AP 81.0.
- **우리 적용:** CommonForms 한국어 2.6% ≈ 1.2만 페이지가 존재한다. 우리 8클래스 GT는 없지만 (a) 우리 모델의 실서식 검증셋 확장, (b) DocSynth식 "실요소 풀"의 원천(텍스트 필드·체크박스 크롭), (c) 비한국어 페이지까지 포함해 "생김새 클래스" 사전학습 소스로 쓸 수 있다.

### Dessurt — arXiv:2203.16618
합성 서식: GPT-2에 "This form has been filled out" 프롬프트로 라벨:값 쌍 생성, 표는 위키 1–3어 헤더 + 랜덤 값, 공간이 다 찰 때까지 랜덤 배치. **폰트 1만 종 이상**(1001fonts 무료 상용 전부), 합성 필기 80만 줄. 합성 서식 제거 시 FUNSD 엔티티 F 50.0→49.0, **NAF(손글씨 역사 서식) 28.2→16.5**.
- **우리 적용:** 실서식과 가장 먼 도메인(NAF)에서 합성 서식의 기여가 가장 컸다 — 즉 합성 다양성은 "학습셋과 다른 테스트"에서 가장 값지다. 라벨어 생성에 LLM(현대판 GPT-2)을 써서 90어→수천 어로 넓히는 직접 선례.

### RIDGE — arXiv:2504.10659 (CVPR 2025)
GPT-4o-mini가 계층 구조 텍스트(HST: h1/h2 태그, "키: 값", 하이픈 중첩)로 내용 생성 → OCR만 있는 실문서 10만 장(RVL-CDIP 서식·이력서·메모, FUNSD, XFUND, HUST-CELL)으로 LoRA 학습한 LLaMA-3.1-8B가 내용 조건부 박스 좌표 생성 → 폰트 교체·헤더 볼드·배경 재질·격자선 추가로 렌더. 영·중 각 3K 문서 → 444K 인스트럭션. Qwen2-VL-7B 오픈셋 F1: FUNSD 59.89→66.48, XFUND-ZH 62.08→69.84, CORD 82.71→84.47.

### Identify, Locate, Link — arXiv:2608.20868
빈 필드를 Qwen2.5-VL-72B가 문맥에 맞게 채워 적응형 폰트 크기로 렌더(합성 채움), 키-값 부그래프를 보존한 크롭 증강. 합성 채움: FUNSD SER 0.523→0.543, XFUND SER 0.376→0.412·RE 0.171→0.206(+20.5%); 크롭 증강이 RE 최대 +41%.

### Synthetic Document Generation for Form Understanding with VLMs — BNAIC 2025 (arXiv 미확인)

## 5. LLM 주도 절차적 변형 — 종합

| 논문 | LLM 역할 | 전이 이득 |
|---|---|---|
| WebSight | 콘셉트(소형)→HTML(대형) 2단계 | Design2Code-18B가 실웹에서 상용 API 근접 |
| Jedi | 컴포넌트 코드 변형 | 혼합 유형 스케일링 포화 없음 |
| Dessurt | 라벨:값 텍스트 생성 | NAF +11.7 F |
| RIDGE | HST 내용 + 레이아웃 LLM | FUNSD +6.6, XFUND +7.8 |
| DocDjinn | HTML 직접 작성 | 실 100장으로 87% |
| Identify-Locate-Link | 빈 칸 채움 | XFUND RE +20.5% |

공통 패턴: LLM은 **어휘·내용·구조 순서**를 넓히고, 렌더링·GT는 결정적 코드가 담당한다(LLM이 좌표를 쓰게 하지 않음). 우리 구조(문법 샘플러 + 부품 함수 + lint)는 이 분업에 이미 맞다.
